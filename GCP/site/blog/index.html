build IaC ~3 min read

1) Why IaC-first matters (even for “simple” sites)

Cloud projects fail in boring ways: missing steps, inconsistent environments, and “it worked yesterday.” IaC fixes that by making infrastructure repeatable, reviewable, and version-controlled.

  • Every change becomes a commit with history
  • Setup becomes predictable and teachable
  • You can rebuild from zero without panic

For this project, I’m treating the static website like a production system: code-defined resources, automated deploys, and explicit cost awareness.

public Web ~4 min read

2) Static doesn’t mean “easy”: DNS, HTTPS, and caching

The hard part isn’t writing HTML. The hard part is making your site reachable, fast, and secure—under your own domain.

  • DNS can be simple until it isn’t (records, TTLs, propagation)
  • HTTPS is non-negotiable for credibility
  • CDNs help performance—and can hide mistakes if you don’t understand caching

I’m using Cloudflare for CDN/DNS to control cost and keep performance strong. The goal is still the same: understand what’s happening at the edge.

3) Visitor counter: tiny feature, real architecture

A counter looks trivial, but it forces real backend thinking: data storage, an API boundary, auth, CORS, and deployment.

  • Frontend calls an API endpoint (not the database directly)
  • API updates a database value
  • Deployment is automated with tests

Next phase: Firestore + Cloud Function (or Cloud Run) + API Gateway, provisioned via Terraform, deployed via GitHub Actions.
